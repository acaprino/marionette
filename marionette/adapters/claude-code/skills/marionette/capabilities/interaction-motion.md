# Interaction Motion (build and review how an interface moves and responds)

Every interaction answers six questions in this order: should it move, does it answer at once, where should the eye go, how should it move, can people find it, hit it, choose it and type into it, and can they finish. A later answer never rescues an earlier one. `<UA>` below stands for `<package_root>/scripts/charles-skills/skills/design/charles-ux-animation`. The method is `<UA>/SKILL.source.md`; exact values for common components are in `<UA>/references/recipes.md` and the techniques in `<UA>/references/techniques.md`. Both references open with a contents line: read the section a step points to. Each original is the full version and wins where this body differs, except for the changes listed in the Sources section.

## Behavior

1. **Match the stack** (`## Run it`). Find what the project already animates with (CSS transitions, Tailwind, Motion as `motion` or `framer-motion`, React Spring, WAAPI) and write in that. State changes stay in CSS transitions. If Motion is installed, use it only for what CSS cannot do: animating an element out as it unmounts, layout changes, and springs that follow a finger. Never add a library for what a CSS transition does, and never hand-roll a spring where Motion is installed.
2. **List the interactions** in scope: what starts each (pointer, touch, keyboard, network, scroll), how often one person fires it in a day, and what it has to tell them. Then cut, or in a review flag, every element and step that does not serve the task (Occam's razor, question 6) before polishing anything.
3. **Should it move?** (`## 1. Should it move?`). The frequency tree: from the keyboard or many times a day (lists swept with the pointer, toolbars, tabs, palettes — hover highlights included) means no animation; a few times a session means animate within the timing table; a moment not repeated today may be choreographed, each move up to 500ms and the whole sequence up to 2.5s. Motion that answers no question is cut. Tooltips after the first skip both the 600–700ms delay and the transition (and keyboard focus shows a tooltip at once). On first page load, nothing plays an entrance just for being there (`AnimatePresence initial={false}`).
4. **Does it answer at once?** (`## 2. Does it answer at once?`, Doherty threshold 400ms): the pressed state shows on the same frame as input; update optimistically when an action almost never fails (rollback with message on refusal); a delete, archive or send leaves immediately with Undo in a toast for at least 5s (confirm only what cannot be undone); final submits disable the trigger at once, show a spinner or "Saving…" only after 300ms and held at least 500ms once shown; past 1s show a skeleton the size of the result.
5. **Where should the eye go?** (`## 3. Where should the eye go?`): staging (one primary motion at a time), stagger (copies 40–70ms apart, only the first 6; distinct pieces of one section 80–100ms apart; content inside a moving container arrives with it), Von Restorff, serial position, secondary action (rare moments only) and exaggeration (error shake 360ms, never on blur or neutral changes).
6. **How should it move?** (`## 4. How should it move?`): the timing table (press, hover, colour 100–150ms; tooltip 125ms; dropdown, popover, select 150–250ms; modal, drawer, sheet, toast 200–300ms; moving or resizing in place 200–300ms; page transition, shared-element move or flying item 300–400ms; rare choreographed moment up to 500ms a move). Exits are 20–30% shorter than their entrance, and quieter. Curves by the tree of `### Easing` (a spring `{ type: "spring", duration: 0.5, bounce: 0 }` for what follows a finger; ease-out `cubic-bezier(0.32, 0.72, 0, 1)` for both entering and leaving — never ease-in in product UI; ease-in-out `cubic-bezier(0.77, 0, 0.175, 1)` for moving/resizing on screen; `ease` 150ms for hover/colour; linear only where the motion is time itself), custom curves never built-in CSS keywords for movement, never `transition: all`. Then origin (grow popovers from their trigger; popovers/menus start at `scale(0.95)`, tooltips/modals at `scale(0.97)` with `opacity: 0`, never `scale(0)`), anticipation/press/hover (`scale(0.97)` on `:active`, never below 0.95; dense all-day controls darken background instead; hover only under `@media (hover: hover) and (pointer: fine)` on a stationary parent), arcs (bulging 10–20% with scale up to 1.3 and shadow), follow through, squash and stretch, pose to pose, solid drawing, meaning (odometer number roll with `tabular-nums`), swap in place (stack both at once, `AnimatePresence mode="popLayout"`, 2px blur between icons), interruptibility, sine-wave loops, and `will-change: transform` only to fix shaky animations. Open the matching section of `references/recipes.md` or `references/techniques.md`.
7. **Can people find it, hit it, choose it and type into it?** (`## 5. Can people find it, hit it, choose it and type into it?`): proximity, similarity, uniform connectedness, Prägnanz, Fitts's law (targets at least 44×44px on touch and 40×40px with a pointer; Cancel takes default focus in a destructive confirmation), the pseudo-element hit-area recipe (never below 24×24px where two zones overlap), Hick's law (groups of 7 or fewer; never pre-select anything that costs money or shares data), Miller's law (chunk past 5 units), Jakob's law and Postel's law (parse every common form; validate on blur or submit, never while a field is first being typed).
8. **Can people finish?** (`## 6. Can people finish?`): Tesler's law, Parkinson's law, Occam's razor with progressive disclosure, the Pareto principle, errors (prevent, then recover with Undo for reversible actions), Zeigarnik effect with goal gradient, and the peak-end rule.
9. **Name the numbers.** Durations, curves and springs live in named tokens (custom properties, theme, or one constants file), and every animation uses them. A sequence of three or more stages gets a storyboard (`references/techniques.md`, `## Storyboards`).
10. **Verify** with the eleven checks of `## Verify` (scrub at 10% speed, interrupt, hammer the keyboard, sweep the pointer across lists/toolbars/tooltips, slow the network and force failures, tap the edges on a phone, paste messy input, finish every flow, reduced motion, switch the theme, the tenth use). In a code-only review do not build a harness: after the findings, list the checks you could not run and what each would catch.
11. **Review** (`ui.interaction-review`): change nothing. Open with the interaction list, then one table row per finding: severity, rule, where (file and line, or frame), before, after. Severity is **broken** (a wrong result, lost input, a blocked or skipped step, unreachable for keyboard/screen-reader, motion hiding what people need or ignoring reduced motion), **friction** or **polish**; sort by severity, then by the six questions (bugs no rule covers use `"no rule"` and sort with the rest).
12. **Record** `interaction_changes` (files and what changed, with the tokens added; `none` for a review) and `interaction_report` (the review, or for a build the checks run with their results, those not run and what was reported instead of changed).

## Specifics

- **Recorded motion comes first.** The confirmed motion values of a project `DESIGN.md` that is not a starter or a reference, then a recorded `motion-spec` and `reduced-motion`, decide durations, curves and reduced-motion alternatives where they differ from this method's table and trees; a Master or recorded `constraints` that limit motion do the same. With none recorded, the source's values apply as written. The design file is never rewritten in this step (`design-file` owns it).
- **Reduced motion.** The source turns every animation off under `prefers-reduced-motion: reduce`, fades included, with the same end states and information; the one exception is an indicator that work is still happening. A recorded `reduced-motion` that keeps opacity fades is followed instead, and the report says so.
- **Beside design guidance.** A recorded `design_candidates` or `stack_guidance` is a set of proposals. Where the lookup data and this method agree on a value, use it: exits 30% shorter than entrances satisfy both, as does a press scale of 0.97, and 48dp on Android satisfies both target minimums. Where they differ with no common value (the lookup data prefers spring curves and confirms before destructive actions; this method keeps springs for what follows a finger and gives Undo to what is reversible), follow this method and name the difference in the report.
- **Scroll.** Scroll-linked animation is the scroll-code step's. This step animates what people trigger.
- Nothing is installed: the method adds no library the project does not have.

## Checks

- **interactions_listed_first**: every interaction in scope was listed with its trigger, its frequency and what it has to tell people, before any change or finding.
- **questions_walked_in_order**: the six questions were walked in order for every interaction, each subsection applied or skipped because nothing in scope can trigger it.
- **numbers_in_named_tokens**: every duration, curve and spring the step wrote is a named token, and a sequence of three or more stages has its storyboard.
- **stack_matched**: the animations are written in what the project already animates with; no library was added for what a CSS transition does.
- **recorded_motion_respected**: no value of a recorded motion specification, project design file or Master was contradicted; where the method differs, the recorded value was used and the difference reported.
- **reduced_motion_holds**: under `prefers-reduced-motion: reduce` every end state and every piece of information is the same as with motion on, by the source's rule or the recorded alternative.
- **findings_in_source_table**: the review opens with the interaction list and every finding is a row with severity, rule, where, before and after; no file was changed.
- **unrun_checks_listed**: every verification check that could not be run is listed with what it would catch.
